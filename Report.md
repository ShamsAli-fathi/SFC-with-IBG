# Paper Draft and Lightweight Testbed Comparison

Date: 2026-07-01

## Purpose and scope

This report compares the container and testbed design described in `misc/vesal_tex.tex` with the implementation currently present in this repository. It focuses on what is genuinely the same, what was simplified to make the testbed lightweight, and which paper claims are not implemented or validated by the current code.

The comparison is based on repository code, Kubernetes manifests, tests, and the recorded Phase 6 validation. It does not treat a design written in the paper as implemented unless corresponding evidence exists in the repository.

## Short conclusion

The current system preserves the main scientific control loop: flows arrive in sequence, choose exactly one replica at every stage, experience load-dependent utility, observe only selected replicas, update beliefs, and repeat until the existing equilibrium rule is satisfied. The exact decoupled `BR_EIBG` solver, utility calculation, learning rule, placement representation, SLA calculation, Jain fairness, and equilibrium test are reused by both the simulation and Kubernetes paths.

The major difference is the meaning of a “CNF container.” The paper describes a hybrid telecom-oriented dataplane with kernel and DPDK/VPP CNFs, packet generators, sidecars, resource emulation, and a monitoring stack. The repository instead uses small Python/FastAPI HTTP services as CNF stand-ins. This retains real containers, Pods, service discovery, multi-hop traffic, contention, and latency measurement, but deliberately does not reproduce a real 6G user plane or accelerated packet processing.

In simple terms: the implemented testbed is faithful to the IBG decision-and-learning experiment, but it is a lightweight functional model of the container dataplane rather than the full dataplane described in the paper.

## What is preserved without a mathematical change

The following behavior is not merely similar in spirit. It is the same reference Python logic used through adapter boundaries in both backends:

1. **Decoupled per-stage game.** Each stage is solved independently under the existing no-cross-stage-coupling assumption.
2. **Sequential admission order.** The flow list is randomized per stage, and placements are made in that sequential order.
3. **Exactly one replica per stage.** Every flow receives one and only one replica choice at each configured stage.
4. **Exact continuation reasoning.** `br_eibg_exact` explores continuation play over all active replicas for the small instance and memoizes subgames by the complete load vector. It is not replaced by a Kubernetes-specific heuristic. This implements the paper's formal one-replica-per-stage constraint as a one-of-many choice; it deliberately does not copy the draft's literal binary choose/skip pseudocode shape.
5. **Belief-driven utility grid.** The existing Monte Carlo quality sampling and replica utility function build the utility values used by the exact solver.
6. **Load-dependent negative externality in the model.** The final number of flows assigned to a replica remains the congestion input to the legacy observation and utility behavior.
7. **Asymmetric observation rule.** Only replicas selected by a flow provide that flow's observation; idle replicas do not generate equivalent raw samples.
8. **Local belief update and aggregation.** Kubernetes telemetry is converted back into the existing `Observation` contract before the reference learning functions run.
9. **Existing outcome measures.** Aggregate and per-flow utility, SLA violations, Jain fairness, elapsed time, beliefs, and the existing equilibrium rule are calculated by the same functions.
10. **State across slots.** Experiment mode retains one evolving replica and belief state until the existing equilibrium condition is reached or the configured iteration bound is exceeded.

There is one careful bridge between physical execution and mathematical preservation. Real HTTP concurrency can vary slightly because operating-system and network scheduling determine which requests overlap. The flow generator therefore sends each replica the solver's final assigned load as `legacy_congestion`, while also recording actual admitted concurrency as separate runtime telemetry. This prevents accidental changes to the IBG observation model while still exposing real container behavior.

## What remains genuinely real in the lightweight version

“Lightweight” does not mean that Kubernetes and networking are simulated away. The implementation still exercises:

- real Docker images and non-root containers;
- a real kind Kubernetes API server and containerd-backed cluster nodes;
- StatefulSet Pod creation, scheduling, readiness, stable ordinals, and Pod DNS;
- readiness-filtered Pod discovery using an in-cluster ServiceAccount;
- controller-to-flow-generator and flow-generator-to-replica HTTP communication;
- complete selected routes through multiple independently running replica Pods;
- concurrent logical flows and measurable request overlap;
- actual server-side processing time, client request latency, Pod identity, node identity, and endpoint metadata;
- failure detection for missing Pods, bad HTTP responses, identity mismatches, and correlation mismatches.

Therefore, the repository is a real orchestration and service-to-service testbed. What it does not provide is a realistic telecom packet dataplane.

## How the lightweight substitutions work

### 1. HTTP replicas instead of full CNFs

Each replica is a tiny FastAPI service. `/health` supports Kubernetes probes and identity checks. `/process` represents work performed by a selected network-function replica. Configured base delay represents normal processing cost, while an extra delay per overlapping request creates a controlled congestion effect.

This is enough to test whether the IBG controller chooses endpoints, forms correct chains, observes selected replicas, and responds to load. It is not enough to measure packet throughput, queue disciplines, NIC behavior, or true AMF/SMF/UPF processing.

### 2. HTTP route runner instead of packet generators and service-mesh chaining

The controller gives the flow generator a complete route for every logical flow. All flows begin concurrently, but each flow waits for stage 1 before calling stage 2, and so on. This gives the intended ordered SFC behavior with very little infrastructure.

The trade-off is that the traffic is request/response HTTP, not controlled-rate TCP/UDP or DPDK packet bursts. Consequently, the testbed can study placement logic and application-level contention, but not line-rate forwarding.

### 3. Deterministic profiles instead of hardware classes

Replica profiles encode hidden state, capacity, delay, cost, congestion penalty, and observation seed. They produce stable, repeatable differences among replicas without requiring dedicated cores, NUMA placement, hugepages, or a special NIC.

This preserves experimental heterogeneity at the model level. It does not demonstrate that a real DPDK Pod outperforms a kernel Pod.

### 4. Direct telemetry instead of Prometheus, Grafana, and sidecars

Each `/process` response includes identity, concurrency, latency, and legacy observation fields. The flow generator correlates these fields by slot, flow, stage, and replica, and returns them directly to the controller.

This makes the evidence easy to test and removes several services from a laptop-sized cluster. The cost is that the current system has no time-series monitoring, dashboards, queue-depth scraping, or independent metrics pipeline.

### 5. Endpoint selection instead of Pod rescheduling

The solver's action is interpreted as choosing an already-running Pod endpoint. Kubernetes remains responsible for placing the Pods on worker nodes. The controller has read-only discovery permission and does not modify workload scheduling for every flow.

This is a good fit for per-flow SFC selection: moving a Pod would be far slower than routing a flow to an existing replica. It also means that paper statements about applying labels, annotations, or affinity as the placement decision do not describe the current runtime.

## Validation evidence in the repository

The strongest completed comparison is Phase 6 at three stages, five replicas per stage, and three flows, repeated for seeds 2050, 2051, and 2052.

The recorded result is exact parity between the simulation and Kubernetes backends for all 27 placements and for the corresponding sampled utility grids, legacy observation signals and likelihoods, beliefs, aggregate/per-flow utility, SLA results, Jain fairness, and equilibrium results. Kubernetes additionally returned complete Pod, node, endpoint, concurrency, and latency metadata for every hop.

Timing was intentionally different: the recorded Kubernetes mean was about 0.309 seconds per slot versus 0.051 seconds in-process, or roughly 6.04 times slower, because Kubernetes execution includes API, DNS, HTTP, and telemetry overhead. That difference is expected and is not a mathematical discrepancy.

This validation supports the statement that the lightweight container path preserves the reference IBG behavior for the supported case. It does not support the draft's separate claims about DPDK/kernel performance, line rate, Prometheus overhead, `tc/netem` robustness, large-scale approximation algorithms, MILP/DRL comparisons, or specific sub-100-ms controller performance.

The word “exact” also needs a narrow interpretation. It means exact continuation play over the already sampled utility grid for the small decoupled game. It does not mean that the complete paper system, coupled problem, physical network, or large deployment is solved exactly.

## Claims that should be kept separate

Based on the current repository, the following statements are safe:

- The system runs the exact decoupled IBG control loop in Kubernetes at the supported small size.
- Logical flows are mapped to real, Ready Pods and exercise real multi-hop HTTP routes.
- Only selected replicas produce observations.
- Belief, utility, SLA, fairness, and equilibrium results match the controlled simulation for the three validated seeds.
- Kubernetes-specific latency, concurrency, Pod, node, and endpoint telemetry is collected.

The following statements are not supported by this implementation:

- The Pods are real AMF, SMF, UPF, or production telecom CNFs.
- DPDK or VPP is running or has been compared with the kernel path.
- Hugepages, VFIO, SR-IOV, RSS, NUMA tuning, CPU isolation, or a 10 GbE NIC has been validated.
- `iperf3`, `pktgen-dpdk`, OVS, NSM, `tc/netem`, Prometheus, or Grafana is part of the current experiment.
- Measured HTTP latency directly drives the belief update; it currently remains separate from the preserved legacy signal.
- Candidate pruning, limited-lookahead, Monte Carlo, coupled/budgeted IBG, MILP, DRL, or large-scale benchmark claims have been implemented by this testbed.
- The current results demonstrate line-rate throughput, production 6G behavior, autoscaling, Pod churn robustness, or large-cluster scalability.

## Overall assessment

The implementation makes a deliberate exchange: it gives up dataplane fidelity and large-system breadth in order to make the experiment reproducible on one modest machine and to protect the reference IBG mathematics.

That exchange preserves the main testbed goal well. The repository can answer, with real Kubernetes components, “Does the controller discover replicas, choose one per stage, run selected chains, collect asymmetric observations, update beliefs, and reproduce the simulation's mathematical outcome?” The validated answer is yes for the supported small configuration.

It cannot yet answer, “How does this perform as a real accelerated 6G dataplane?” That would require the hardware, CNF classes, packet generators, link emulation, and monitoring components described in the paper but intentionally omitted here.

The cleanest description is therefore: **a lightweight Kubernetes realization of the paper's IBG control and learning plane, using HTTP CNF test doubles in place of the paper's hybrid kernel/DPDK dataplane.**
